# diagnose — 原因を言う前に

読むタイミング: 「〜が原因だ」と口に出す・書く直前。修正方針を決める直前。

**汎用の裏取り規律は global の `my-verify-before-asserting`。** ここに置くのは
このアプリで**どの観測がどの仮説を決着させるか**だけ。

## 何を防ぐか

同じセッションで診断を 3 回外した。

- 「dev サーバの watch 再起動でシェルが消えた」→ 実際は該当の編集では再起動しない
- 「全角文字の描画幅が見切れの原因」→ 実際は tmux のウィンドウ寸法の不一致
- 「WebGL レンダラーが解決策」→ 依存を足したが今回の問題には無関係だった

いずれも**観測していない因果を断定**した。共通していたのは「ログの近くにあった事象を
原因として結び付けた」こと。

## 原則

> 因果を述べるときは、**その主張が偽なら違う結果になったはずの観測**を 1 つ挙げる。
> 挙げられないなら「未確認」と書く。

- **ログの近さは根拠ではない。** 同時に起きたことと、起こしたことは違う
- 仮説は 2 つ以上立て、**どちらを否定できるかで観測を選ぶ。** 1 つの仮説を確認するだけの
  観測を選ばない（確証バイアスになる）
- 「〜のはず」「たぶん」で組み立てた因果を、次の文で断定に格上げしない

## 観測レシピ

| 主張したいこと | 決着させる観測 | その観測が示さないこと |
|---|---|---|
| 「dev サーバが再起動した / しなかった」 | 起動しているコンソールに `server source changed; restarting preview server` が出たか。**出ていなければ再起動していない。** 何を編集すると再起動するかは `orientation.md` の表 | バンドルが焼き直されたかどうかは別。views / app.ts の編集は再起動せずに焼き直す |
| 「CSS / HTML の変更が反映されない」 | `CODE_VIEWER_DEV=1` で起動しているか。SSE の `reload` が飛んだか | 遅延バンドル（xterm / shiki / mermaid / yaml / highlight）は dev で焼き直されない。`pnpm run build:web` が要る |
| 「端末の表示が見切れる」 | **サーバ側**: `list-panes -a -F ...` / `list-clients -F ...` が返すウィンドウ・ペインの寸法（`server/tmux/panes.ts` / `clients.ts` と同じ形式）。**クライアント側**: fit addon の `proposeDimensions()` が返す cols/rows。**両者を突き合わせる** | フォント幅は**別の仮説**。主張するならセルを実測する。tmux の寸法不一致とフォント幅は互いの証拠にならない |
| 「環境が壊れている」 | `/_doctor` エンドポイント、または `code-viewer doctor` | アプリのロジックの正否。doctor は環境しか見ない |
| 「UI が正しい / 壊れている」 | dev サーバ（既定ポート 64160）を Browser Pilot で開き、対象要素の **DOM と `getComputedStyle`** を読む | ソース文字列の検査。`style.css` に文字列があることは、その規則が実際に適用されていることを意味しない（→ `testing.md`） |
| 「レイアウトが密度モードで壊れる」 | `body[data-sidebar-font-size]` を 4 値（既定 / compact / large / xlarge）切り替えて実測 | 既定モードだけの確認 |
| 「リクエストが競合した / 古い応答が勝った」 | 応答の `generation` と view 側のカウンタを突き合わせる | ネットワークの遅さ。遅いことと、古い応答が反映されることは別問題 |
| 「バンドルが重くなった / 軽くなった」 | 変更前後の `ls -l web/*.js dist/code-viewer.js` | 体感速度。どのバンドルに載ったかで意味が変わる（→ `dependencies.md`） |

## UI を実画面で確認する

UI 変更は、**振る舞いが正しいと言う前に実画面を見る。**

1. dev サーバを起動する（`pnpm run dev`、既定ポート 64160）
2. Browser Pilot で対象のルートを開く
3. 対象要素の DOM 構造と `getComputedStyle` を読む
4. ユーザーが参照 UI を指しているなら、**その参照実装も同じ手順で読み**、構造を比べる

light / dark 両方を見る。レイアウトを変えたなら密度モード 4 種も見る。

## 報告の書式

因果を報告するときは 3 点セットで書く。**「未確認」の欄を空にしない。**

```
観測: <実際に見たもの。コマンドの出力・DOM・ログの実文言>
そこから言えること: <観測から直接導けることだけ>
未確認: <確かめていない前提・別仮説として残っているもの>
```

「原因は X です」とだけ書かない。X を否定できたはずの観測を並べて初めて断定になる。

## やってはいけないこと

| 違反 | なぜ |
|---|---|
| ログに近い事象を原因として結ぶ | 3 回外した経路そのもの |
| 依存を足して「これで直るはず」と報告する | 効いたかを確認する観測を決めていない（→ `dependencies.md`） |
| ソース文字列の存在をもって UI の正しさを主張する | 適用されているかは別。実際に無関係な規則を守っていたテストが存在した |
| 1 モード・1 テーマだけ見て「直った」と言う | 密度モードと light/dark で壊れ方が変わる |
| 「未確認」を書かずに断定する | 次の人が確認済みだと誤解して、その上に推論を積む |
