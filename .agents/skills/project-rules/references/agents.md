## 1. 全体像

tmux の全ペインを「プロジェクト → エージェント」でまとめて見せ、入力待ちと完了に気付かせ、
claude / codex の複数アカウントを使い分け、登録したプロジェクトの間を同じタブ・同じポートで移る機能群。

| 画面 | 置き場所 |
|---|---|
| 左のサイドバーの「プロジェクト → エージェント」（どの画面にも出る） | `views/agents/agents-sidebar.ts`（枠の畳む・幅は `views/shell/app-nav.ts`） |
| エージェントの全体ボード（サイドバーの「PROJECTS」の横のボタン、`/agents`、`g a`） | `views/agents/agents-view.ts` |
| 最下段の件数（入力待ち n・作業中 n）と使用量 | `views/agents/agent-status.ts`・`views/agents/usage-status.ts` |

| 設定の「エージェントの通知」「エージェント連携」「アカウント」の節 | `views/viewer-settings.ts`・`views/agents/agent-hooks-settings.ts`・`accounts-settings.ts` |
| 左の列の頭（`#left-head`。左の列を畳んだときだけタブ列の左の `#tabs-lead`）のプロジェクト名 = プロジェクトの切替（`p`） | `views/projects/project-switcher.ts`（置き場所は `views/sidebar.ts` の `placeSidebarToggle`、サイドバー・全体ボードと共有する操作は `project-actions.ts`、⋯ のメニューは `project-menu.ts`） |

| サーバ側 | 役割 |
|---|---|
| `server/terminal/activity.ts` | tmux の全ペインを巡回して画面から状態を推す |
| `server/terminal/agent-state.ts` | 状態の記録（メモリだけ）。申告と画面の優先関係はここ |
| `server/terminal/overview.ts` | `/_agent/overview`。ペイン・プロジェクト・サーバ・アカウントを 1 つの応答にまとめる |
| `server/terminal/hooks.ts`・`hook-report.ts`・`statusline.ts`・`settings-file.ts` | フック・statusLine の入れ外しと、フックからの申告 |
| `server/accounts/` | アカウントの登録簿・プロセスの環境変数・ログイン状態・使用量・起動 |

| `server/entry/` | 入口のサーバ。`/p/<鍵>/…` の取り次ぎ・裏のプロセスの起動と本人確認・`entry.json` |
| `server/terminal/unread.ts` | 未読（サーバのメモリ） |

**前提: 入口 1 つ + プロジェクトごとの裏のプロセス。** ユーザーが起動するのは入口の
サーバ 1 つ（ポートも 1 つ）。プロジェクトに依らないもの（この領域の全部: 一覧・巡回・
フックの受け口・未読・アカウント・登録簿・シェル）は入口が持つ。リポジトリ決め打ちの
閲覧は、今までの 1 プロセス = 1 リポジトリのサーバを入口が「裏」として起こし、
`/p/<鍵>/…` を取り次ぐ（取り次ぎの規則は `server.md`「入口のサーバと取り次ぎ」）。
裏は巡回もフックの受け口も持たないので、**状態を持つのは入口だけ**。

`--standalone` の 1 つで完結するサーバ（テスト・スクリプト・古い使い方）は
今までどおり自分で巡回する。混ざる間は、フックの申告と「読んだ」を入口と
1 つで完結するサーバの全部へ送る（裏へは送らない）。ただしフックの申告は、現在の版が
書いた起動ごとの本人確認情報を持つ相手だけに送る（`hook-report.ts` の `reportTargets`）。

## 2. 状態の決まり方

状態は 4 つ（`core/agent-state.ts` の `AGENT_STATES`）。

**並びは画面で 2 通り。混ぜない。**

| 画面 | 並べる関数 | 並び | 理由 |
|---|---|---|---|
| エージェントの全体ボード | `groupAgentPanes` | 入力待ち → 完了・未読 → 作業中 → 待機（`STATE_RANK`） | 「いま手が要るものを上から片付ける」画面 |
| 左のサイドバー | `groupAgentPanesByPlace` | プロジェクトは登録順 → 未登録（名前の順、同名はパスの順）。行は tmux の場所（セッション名 → ウィンドウ番号 → ペイン番号） | 行が勝手に上下すると押そうとしたものが逃げる。気づかせる役目は行の印・畳んだ見出しの印・最下段の件数・通知が持つ |

サイドバーは 2 つの区画に分ける。上 (「PROJECTS」) は登録したプロジェクトで、エージェントが
居なくても常に 1 行。下 (「tmux で検出」) は未登録でエージェントが居るもの。起動・終了で
出入りするのは下の区画だけで、上の行の位置は動かない。0 件なら下の区画ごと出さない。
プロジェクト見出しの印は、人の番のもの（入力待ち > 完了・未読 > 作業中）があればその印、
無ければフォルダで、サーバを起こしている最中だけ回る点線と「起動中…」を優先する。
見出しは `+` と `⋯` の幅を常に確保し、畳んでいてもこの印で中の状態を伝える（件数は最下段）。
エージェントの行は状態の印・種類・作業内容・経過時間・未読を出す。経過時間は
変わった瞬間を見たもの（`updatedAt` が 0 でない）だけに出し、見始めてからの下限しか
分からないものは「—」にしてツールチップに下限を出す（`views/agents/agents-sidebar.ts` の `ageText`）。
選択の見た目は 2 段で、いま見ているプロジェクトの見出しは控えめな面だけ、メインの面で
開いているエージェントの行が強い選択（面 + 細い枠 + 内側の光）。

**ターミナルはメインの面のタブでも映す。** 決まりは次のとおり。

- メインの面は 1 面か左右 2 面。左はファイルと画面を含む全種類、右は terminal と image だけを
  置ける（`core/main-tabs.ts` の `canPlace`）。Files はタブではなく、左で何も選んでいないときの本文
- 窓が 2 面を出せない幅になると、右の面は閉じずに預けて隠す（`core/main-tabs.ts` の `parkRight` /
  `unparkRight`、`views/main-tabs/main-tabs-view.ts` の `fitToWidth`）。分割の操作が印の色になり、
  題名で預けたタブの数を出す。広がれば同じ比で戻す。保存するのは預けた分を含む配置
- タブ列の `+` は `app.ts` の `openNewTabMenu` / `newTabMenuItems` が作る。ファイル、新しいシェル、
  既存のシェルと tmux ペインを開き、全プロジェクトの一覧へも移れる
- エージェントを開く既定は現在の面のタブ（`app.ts` の `openAgentPane`。サイドバー・パレット・
  全体ボード・通知・最下段）。サイドバーの Alt+クリックと、行の右クリックのメニューの項目は
  反対のメインの面に開き、1 面なら右の面を作る（`agents-sidebar.ts` の `openPane(pane, "opposite")`）。経路はどちらも `/_tmux/open`（ペイン → そのセッションのシェル）で、
  タブの中身はシェル（`shell-…`）
- ペインが別のプロジェクト（移れるもの）のものなら、開く前にそのプロジェクトへ移る。判定は
  `core/projects.ts` の `agentPaneTarget` 1 か所（入口は `views/agents/agent-pane-opener.ts`）で、
  移り先の URL に `?open-pane=%N` を付け、移った先が読み込み後にそのペインをタブで開いて
  URL から外す（`core/routes.ts` の `parseOpenPaneOverlay`。`?terminal=` は映しているシェル、
  `?pane=right` は右の面で、どちらとも別のキー）。移った先では判定を通さない（食い違いで移り直しを
  繰り返さない）。git の外・サーバに繋がらないプロジェクトのペインは、今の画面で開く
- xterm は `views/terminal/terminal-view.ts` の枠（`ScreenSlot`）ごとに 1 つで、枠はメインの面の
  左右それぞれの 2 つ。**同じシェルを 2 か所に描かない**。左の面 ⇄ 右の面の移動は枠を
  入れ替えて DOM の親を変えるだけ（attach し直さない）。画像の棚は枠の一部なので一緒に移る
- 棚の項目とターミナルの画像パスを押すと画像のタブで開く (2 面なら反対の面、`other-if-split`)。
  覆い (拡大表示) は Alt / Shift + クリックか、棚の項目の右クリックのメニュー
- URL の `?terminal=<shell>` は、そのシェルのタブを前面にする。下パネルは Tools / Search 専用で、
  開閉は URL に載せない。互換性のため名前を保つ設定 `terminalPanelOpen` は下パネル全体の開閉を表す
- ターミナルのタブを閉じても、シェルもエージェントも止めない。止める操作はタブの右クリック
  メニューの「セッションを停止」で、確認してから行う
- シェルの端末名 (`tty`) はシェルを作った直後から 2 秒まで `ps` で取り直す。まだ空なら、
  シェルとペインの対応 (`shownInShell`) を調べるたびに再取得し、取れた値を覚える。
  同じ tmux セッションをもう一度開く判定は、TTY より先にサーバが覚えた接続先を使う。
  それでも空の間だけ、画面はタブで開いたときの対応 (`TAB_SHELL_PANES`) で補う
`done` を `idle` と分けてあるのは、「終わったのに気付いていない」ものを待ちと同じ強さで
拾うため。申告の `done` はフックからしか来ないので、フックが無いときは「作業中 → 待機」を
見てまだ読んでいないもの（未読の `finished`）を画面では `done` に出す。決まりは
`core/agent-overview.ts` の `withFinishedAsDone` 1 か所で、`views/agents/agent-monitor.ts` が
一覧を受け取るたびに当てる（見出しの印・全体ボードの並び・パレットはこの結果を読む）。
読めば未読が解けて待機に戻る。サーバの状態の記録（`recordAgentState`）は変えない。

### 出どころと優先関係

| 出どころ | 何を根拠にするか | 強さ |
|---|---|---|
| `hook` | エージェント自身のフックの申告（4） | 最も強い。画面の推測では原則上書きしない |
| `screen` | 画面の文言のルール（`core/agent-screen.ts` の `DEFAULT_AGENT_SCREEN_RULES`） | 待機・入力待ちのルールに当たれば申告を上書きできる。作業中のルールで上書きできるのは、画面が動き続けたとき（下の `activity` と同じ条件）だけ |
| `activity` | 画面が動き続けているか止まったか | 最も弱い。申告を上書きできるのは、`OVERRIDE_MOTION_MS` の間ずっと動き続けて「作業中」に戻す場合だけ |

- **申告の `done` は、画面の観測では消さない。** 画面には直前の作業表示や入力欄が残るので、
  それを根拠に完了・未読を消すと「終わったこと」に気付けなくなる。消せるのは `read` と
  新しい申告だけ（`recordAgentState` の冒頭）
- 申告どうしは出来事の時刻（`at`）で比べ、古いものを捨てる。フックは別プロセスから HTTP で
  届くので、`progress` が `stop` より遅れて着くことがある
- 状態はサーバのメモリにだけ持つ。サーバを再起動すると消え、次の申告と巡回で入り直る
  （古い状態をディスクから戻すと、終わったものを「待ち」と出す害のほうが大きい）
- tmux の pane id はサーバを起動し直すと再利用される。巡回ごとに `tmux/command.ts` の
  `readTmuxServerGeneration` で pid と開始時刻（得られなければ socket の inode と ctime）を
  世代として読み、状態・画面観測・未読の鍵は
  **世代 + pane id** にする。世代が変わったら state・seen・unread・前回一覧を一緒に捨てる。
  フックの pane id は、その時点の世代へ付く

### 経過時間を断定しない（`changeObserved`）

見始めた時点で既にその状態だったものは、**いつからそうなのか分からない**。以前はサーバが
見始めた時刻を「状態になった時刻」として出していたため、何時間も待機しているペインが一律
「7分」になり、画面ルールに当たらない codex だけ「–」になって表示が割れた。

いまは、状態の変化を実際に見たとき（観測中の変化か申告）だけ `changeObserved` を立て、
それ以外は時間を出さず「–」とし、ツールチップに「少なくとも N 分前から」と下限だけを出す。
**経過時間を出す処理を足すときは、この区別を落とさない。**

### 巡回の間隔

| 値 | 理由 |
|---|---|
| `ACTIVITY_POLL_INTERVAL_MS`（1.5 秒） | 状態が変わってから一覧に出るまでを 5 秒以内にするため。作業中 → 待機は「待機の表示を 2 回続けて見て」決まるので、2 周 + 画面側の取り直し（`AGENT_MONITOR_INTERVAL_MS`）がそこに収まる値 |
| `ACTIVITY_IDLE_POLL_INTERVAL_MS`・`ACTIVITY_UNWATCHED_AFTER_MS` | プロジェクトごとにサーバが立つので、誰も見ていないサーバまで速く回すと tmux の呼び出しがサーバの数だけ増える（1 本で毎秒約 45 回を実測）。一覧の取得が来ない間は遅く回す。フックの申告は遅くしない |
| `ACTIVITY_CAPTURE_CONCURRENCY`（8）・`MAX_PANES_PER_SWEEP`（24）・`ACTIVITY_SWEEP_TIMEOUT_MS`（6 秒） | capture は固定数の worker で並べ、1 周で扱う数も制限し、巡回を期限内で終える。期限を越えたペインは前回の状態を保ち、`errors` に理由を残す。停止へ丸めない |
| `activityIsStale`（`noteAgentListWatched`） | 古ければ巡回を起動するが、一覧の要求は待たせない。`/_agent/overview` の `observedAt` に最後の巡回完了時刻を返し、0 または古い値なら利用側が古さを判断できるようにする |
| `OVERRIDE_CHANGE_STREAK` を `OVERRIDE_MOTION_MS` から導く | 守りたいのは「12 秒動き続けた」という**時間**。回数の定数のままだと、巡回を 3 秒から 1.5 秒にした時点で 6 秒に縮んでいた。**巡回の間隔を変えるなら、回数で決めている値が無いか探す** |

### hold（作業中 → 待機の見送り）は 1 回まで

作業中から待機の表示に変わっても、画面がまだ動いていれば 1 回だけ切替を見送る
（`nextObservedState` の `held`）。**無制限に見送ると、待機中も入力欄の飾りや時計で画面が
動き続けるエージェントが、いつまでも作業中のまま戻らない**（実際に codex で起きた）。
逆に、見送りがたまたま「作業中の行を拾えないルール」の穴を隠していたこともある。見送りを
延ばして直そうとしない。ルールを直す。

### 画面のルールは、エージェントの表示が変われば必ずずれる

画面の文言での判定は推測であり、エージェントの版が上がれば外れる。実際に外れた例:
作業中のルールが「下から 8 行以内に `thinking` と `tokens`」を条件にしていたところ、
作業中の行は `thinking` を出さない時間帯があり、入力欄の下のステータス表示の行数や、
間に挟まる案内の行で 8 行の外へ出た。その間は入力欄を見る待機のルールが勝ち、作業中の
エージェントが「待機」と出た。

- **ルールを、特定の人のステータス表示の行数に頼らせない。** 作業中の行や入力欄は、
  下からの行数ではなく形で探す（例: 区切り線に挟まれた入力欄、`… (` を含む作業中の行を
  画面全体から探す）
- 1 つの版・1 つのエージェントの文言に寄せすぎない。既存の古い表示のルールを消さない
- 直すときは `.agents/skills/terminal-ai-state-rules/SKILL.md` の手順（実画面の証拠・
  正例と反例・優先度）に従う。原因を言う前に `diagnose.md`
- ずれを根本から減らすのはフックの申告（4）。画面の推測は、フックを入れていない人のための
  下支え

## 3. 通知と未読

`core/agent-overview.ts` の `agentTransition`・`nextAgentUnread`・`shouldNotifyAgent` が
条件の全部。ここは理由だけ書く。

| 決まり | 理由 |
|---|---|
| 知らせるのは「作業中 → 入力待ち」と「作業中 → 止まった」 | 人の手が要る瞬間だけにする |
| 申告の `done` は、直前の作業中を見逃していても「終わった」として扱う | 1.5 秒の取り直しの間に始まって終わったターンも拾うため |
| 最初の取得では何も知らせない。サーバが変わった（`serverInstance` が違う）ときも最初の取得に戻す | 開いた瞬間に止まっているものを全部「今終わった」と言わない。サーバの再起動直後は状態を覚え直す前の「待機」を完了と取り違える |
| タブが前面で、そのペインをいま見ているなら知らせず、未読にもしない | 見ているものに通知は要らない |
| 通知の許可は、一覧の「通知を有効にする」か、最初の入力待ちでサイドバーに 1 度だけ出す案内（`agentNotifyHintDismissed`。許可かブロックを選ぶか、閉じたら二度と出さない。許可の窓を閉じただけで default のままなら、どちらも「まだ許可されていません」と「もう一度求める」を出す。判定は `notifyPermissionView` だけ）を押したときだけ求める | ページを開いた瞬間に許可を求めない。入力待ちが来たときが、通知の要る理由が分かる瞬間 |
| 通知は画面が見た変化に加えて、サーバの未読に新しく載った変化でも出す（`agent-monitor.ts` の `serverOnlyTransitions`） | 背面のタブはブラウザが取り直しを十数秒まで間引き、短い作業中をまるごと見逃す（実測で 17 秒あいた）。通知が要るのはまさに背面にいるとき |
| 通知の `tag` はペインと変化の組 | 同じオリジンのタブが複数あっても重ならない |
| 取り直しの fetch に `BACKGROUND_REQUEST_HEADER` を付ける | 通信中の表示と画面切替の中断の巻き添えにしないため。規則は `server.md` の Request Lifecycle の表 |

最下段の件数（入力待ち n・作業中 n）は、以前のヘッダの件数表示と同じ部品（`agent-status.ts`）を
最下段に置いたもの。押すと全体ボードへ（入力待ちが 1 件ならそのペインを開く）。

**未読はサーバのメモリに持つ**（`server/terminal/unread.ts`。一覧の応答の `unread`）。
入口の下ではプロジェクトの切替がページの読み直しなので、タブのメモリに置くと移るたびに
消えていた。判定は画面と同じ純関数（`agentTransition`）を、状態の記録が変わった瞬間
（`agent-state.ts` の `recordAgentState` → `unread.ts` の `noteAgentStateChange`）に当てる。
一覧を作るたびに比べる形だと、一覧を取りに来るのが背面のタブだけのとき作業中を見逃した。
「見ている」はサーバに分からないので、画面が見ているペイン・開いたペインを
`POST /_agent/unread` で解く（`agent-monitor.ts`）。応答に `unread` が無い古い版の
サーバでは、今までどおりタブのメモリで数える。サーバまたは tmux の世代が変わると消える
（状態の記録と同じ）。

**「読んだ」の中継**（`server/terminal/read-relay.ts`）は、1 つで完結するサーバが並ぶ間の
もの。入口は状態を持つのが自分だけなので中継しない（`relay: true` を受けても送らない）。
1 つで完結するサーバは、入口と、登録簿のうち裏でないサーバへ送る。受け取ったサーバは
送り直さない（送り返しの輪を作らない）。

## 4. フック

エージェント自身に状態を申告させる。画面の推測（2）の弱点（完了が「15 秒動かなかった」
でしか分からない・node として動く claude の種類が分からない）を埋める。

### 何をどこに足すか

| 対象 | 足すファイル | 足すもの |
|---|---|---|
| claude | `<設定ディレクトリ>/settings.json` の `hooks` | コマンド `<状態ディレクトリ>/agent-hooks/code-viewer-agent-hook claude` |
| codex | `<CODEX_HOME>/hooks.json` | 同じ形で `… codex` |
| 両方 | `<状態ディレクトリ>/agent-hooks/code-viewer-agent-hook` | 起動スクリプト（node と code-viewer の場所を持つ） |

出来事と申告の対応は `core/agent-hooks.ts` の `HOOK_SPECS` と `agentEventForHook`（**2 つは
必ず一緒に直す**）。上のコメントに入れなかった出来事とその理由がある。要点:

- **申告にならない出来事は入れない。** 呼ばれるたびにエージェントの時間を使う
- claude の `Notification` は `permission_prompt` と `elicitation_dialog` だけ。`idle_prompt`
  （入力欄で待っているだけ）は完了・未読を入力待ちで上書きしてしまう
- `SessionStart` の `compact` は除く。作業の途中で起きるので、待機に倒すと作業中が消える
- claude は `SessionEnd` 以外を `async` にして待たせない。**codex には async が無い**ので、
  ツールごとに呼ばれる出来事（`PostToolUse`）は入れない。許可の後に作業へ戻ったことは
  画面の観測に任せる

### 出来事を足す・変えるとき

1. 出来事の名前と、フックに渡される JSON の欄を公式ドキュメントで確かめる（claude は
   https://code.claude.com/docs/en/hooks 、codex は https://developers.openai.com/codex/hooks 。
   推測で名前を書かない）
2. `HOOK_SPECS` と `agentEventForHook` を同じ変更で直す。申告にならない出来事は入れない
3. `web-src/test/agent-hooks-core.test.ts` の `agentEventForHook` の表に、足した出来事の行と
   「申告しない入力」の行を足す。テストに snake_case の欄の値を書くなら
   `_hygiene-known-identifiers.ts` に足す（公開リポジトリの検査が落とす）
4. 既に入れている人の行は「一部だけ設定済み」（`hookEntriesState` の `partial`）になり、
   もう一度「入れる」で足りない分だけが足される。**codex は足した分を信頼し直すまで
   実行しない**（下の「codex の信頼」）
5. 動かして確かめるのは 10 の手順。設定ファイルに書かれたコマンドを、公式どおりの入力で
   手で実行して一覧の状態が変わることを見る

### 起動スクリプトを挟む理由

設定ファイルには起動スクリプトの場所と種類だけを書き、node と code-viewer の場所は
起動スクリプトの中に置く（`agentHookCommand`・`hookLauncherScript`）。

- code-viewer の版が上がると場所が変わる。場所を設定ファイルに書くと、そのたびに設定
  ファイルを書き換えることになる
- **codex はフックの定義のハッシュで「信頼」を記録する**。文字列が変わると、利用者が
  `/hooks` で信頼し直すまで実行されない。だから設定ファイルの文字列を変えない
- 呼び先が消えていても、起動スクリプトは終了コード 0 で抜けて理由を失敗の記録に残す。
  設定の節は「呼び先がありません」と出し、「直す」で起動スクリプトだけを書き直す

### 申告の送り方（`hook-report.ts`）

- **入口（`entry.json`）と、登録簿のうち裏でない全サーバへ並べて送る**（`reportTargets`）。
  入口の下では状態を持つのは入口だけだが、`--standalone` のサーバも同じペインを見ているので、
  1 つにだけ送ると状態が食い違う。裏（登録簿の `backend`）は受けない
- **POST より先に `/_entry` で本人確認する。** 入口は 0600 の `entry.json`、単体サーバは
  0600 のサーバ登録簿に起動ごとの token・pid・version を置く。HTTP 側の role・token・pid・
  version が全て一致し、URL が `http://127.0.0.1:<port>/` のときだけ送る。古い版のように
  token や version が無い相手、pid・ポートを使い回した別プロセスには送らない
- 本人確認の失敗は不一致の項目を全部記録する。ただし token とフックの prompt 本文は
  失敗記録へ書かない。prompt を含む POST 本文も本人確認が終わるまで作らない
- `/_agent/action` は本文を 16 KiB までに制限し（超えたら 413）、`lastPrompt` と `note` は
  それぞれ先頭 2,000 文字に切り詰める（`server/terminal/handle.ts` の `MAX_AGENT_ACTION_BODY_BYTES`・
  `textField`）。`at` は 0 以上で現在時刻以下の安全な整数だけを受け入れ、違反は状態を変える前に
  400 で返す
- 1 つあたり `REPORT_TIMEOUT_MS` で打ち切る。1 つが応答しなくてもほかを止めない
- **どう失敗しても終了コードは 0。** エージェントをブロックする終了コードを返さない
- 失敗は捨てず、`<状態ディレクトリ>/agent-hooks/failures.jsonl` に時刻・フック・サーバ・
  理由を残す（設定の節が直近を出す）。本人確認の接続拒否は「確認できなかった」と記録する。
  確認後の POST 直前に相手が終了して接続を拒んだ場合だけは、どこにも届かなかったときに
  拒否した URL を全部並べて 1 件残す
- 登録簿の件数がそのまま 1 回の申告の時間になる（全件を読むため）。古い登録の片付けは
  サーバの起動時に行う（`pruneDeadServerRegistry`。フックの経路では片付けない）

### codex の信頼

codex は新しいフックを、利用者が `/hooks` で信頼するまで実行しない（公式の仕様）。
code-viewer から信頼の操作はしない・できない。入れた後の画面に手順を出すだけ。
**入れたのに codex の状態が変わらないときは、まず信頼されているかを疑う。**

### 設定ファイルを安全に書き換える部品（`server/terminal/settings-file.ts`）

利用者の設定ファイルに書く機能（フック、statusLine）は、必ずこれを通す。新しく書く機能を
足すときも自前で書かない。約束は次のとおりで、どれも実際の要求から来ている。

| 約束 | 守るもの |
|---|---|
| 書く前に読む。JSON として読めない・想定外の形なら書かない | 読めないファイルを上書きして壊さない |
| 確認画面を作ったときの中身のハッシュを持ち回り、書く直前に読み直して違えば書かない | 見せたものと書くものをずらさない |
| 書く直前に同じディレクトリへ時刻付きのバックアップ。失敗したら書かない | 戻せない変更をしない |
| 一時ファイルに書いて置き換える。元の権限を保つ | 途中で落ちても壊れたファイルを残さない |
| リンクはリンクのまま、リンク先を書き換える。バックアップはリンクの側（設定ディレクトリ）に置く | 利用者の設定は dotfiles からのリンクであることが多い。リンク先の管理下にバックアップを散らかさない |
| 自分の分はコマンド文字列の印（`AGENT_HOOK_MARKER`・`STATUSLINE_MARKER`）で見分ける。ほかのツールの分は 1 つも消さず、順序も変えない | 共存 |
| 何度入れても増えない。外すと元に戻る（入れる前から空だった入れ物は、外すときに区別できず片付く） | 入れ外しの往復 |

**書けるかどうかは、リンクを最後までたどった先で判断する**（`writeBlockedReason` は
`realpathSync` で解いた先を見る）。ある開発者の環境で、設定ファイルのリンクの 1 段目が
読み取り専用の場所を指していたのを見て「書けない」と報告し、実際は 2 段先が書けるファイル
だった。人が調べるときも同じ（`readlink -f` と `test -w`）。コード側の判断は
`agent-hooks-server.test.ts` の「a chain of links is judged at its end」で固定している。

書けない設定ファイル（生成物など）は異常ではなく普通にある状態。行は注意の色にせず、
「入れ方を見る」で生成元へ写す手順を出す（`hookRowTone` / `hookRowAction`）。本当の異常
（JSON が壊れている・形が違う・読めない）だけをエラーとして出す。

この機能は外部状態を変えるので、`server.md` の「外部状態を変える機能」の 3 つ（戻し方・
doctor の検出行・消しても検出行を残す）が適用される。doctor のグループは `agent-hooks`・
`agent-accounts`・`projects`。

## 5. アカウントと使用量

アカウント = 種類（claude / codex）と設定ディレクトリの組。claude は `CLAUDE_CONFIG_DIR`、
codex は `CODEX_HOME` にそのディレクトリを渡すと、認証・履歴・セッションがそこに分かれる。
既定のアカウント（変数なし = `~/.claude`・`~/.codex`）は登録しなくても常にあり、消せない。
登録簿は `<状態ディレクトリ>/accounts.json`（起動コマンドと前回の起動の選択も同じファイル）。
「新しく作る」の設定ディレクトリは
`<状態ディレクトリ>/accounts/<種類>-<表示名の slug>`（同名があれば `-2`、`-3`）で、
登録簿の UUID はディレクトリ名には使わない。

### 新しく作るときに共有するもの

「新しく作る」は状態ディレクトリの下にディレクトリを作り、既定のアカウントの設定ディレクトリの
直下にあるものをシンボリックリンクで共有する。分類は `core/agent-accounts.ts` の
`classifyShareEntry`。

| 分類 | 既定 | 決め方 |
|---|---|---|
| 共有する | オン（外せる） | 公式ドキュメントが「利用者が書く設定」とするもの（`SHARED_CONFIG_ENTRIES`） |
| 選べば共有できる | オフ | 公式の一覧に無く、中身を確かめられないもの（プラグイン・利用者が置いたスクリプトなど）。未知の名前は全部ここ |
| 共有できない | 選べない | 認証・識別情報・履歴・セッション・キャッシュ・動作中の状態（`BLOCKED_NAMES`・`BLOCKED_PATTERNS`）と、名前から認証を疑えるもの（`SUSPECT_NAME`） |

- **設定と識別情報が混ざるファイル（claude の `.claude.json`）は共有できない側。**
  迷ったら共有しない側に倒す
- **「共有できない」の検査はサーバでもやる**（`checkShareSelection`。画面を通さない要求も
  拒否し、何も作らない）。画面の検査に頼ると、別の入口から認証情報がリンクされる
- 共有は作るときだけ。既に作ったアカウントのリンクは、後から一覧を変えても変わらない。
  コピーではなく既定の設定へのシンボリックリンクなので、リンク先の設定・フック・statusLine を
  更新した内容は、作成済みの専用アカウント全部へそのまま見える
- 根拠の URL は `SHARED_CONFIG_ENTRIES` と `BLOCKED_NAMES` のコメントにある。名前を
  足すときも公式ドキュメントで確かめ、確かめられなければ足さない（未知のものは既定で
  オフなので、足さなくても共有はされない）
- 「共有できない」に名前を足すときは、`BLOCKED_NAMES` に理由（`auth`・`identity`・`history`・
  `session`・`cache`・`state`）と一緒に足し、`web-src/test/agent-accounts-core.test.ts` の
  「what a new account may share」の表に行を足す。画面とサーバの拒否は同じ分類を使うので、
  ほかは直さなくてよい。名前が snake_case なら `_hygiene-known-identifiers.ts` にも足す

### ログインと「誰として」

- ログインは公式のコマンド（`claude auth login` / `codex login`）を tmux の新しいウィンドウで
  起こすだけ。ブラウザでの承認は利用者が行い、**code-viewer は認証情報を受け取らない・
  保存しない・中継しない**
- 状態は公式のコマンド（`claude auth status --json` / `codex login status`）で得る。
  出力にメールアドレスが入るので、**ログ・失敗の記録・テストには出力の中身を載せない**
  （終了コード・長さ・stderr の先頭だけ。`server/accounts/login.ts`）
- **codex の「誰として」は出さない。** `codex login status` は方式しか返さず、誰としてかは
  秘密を含む認証ファイルを開かないと分からない。開かない。区別は利用者が付けた表示名でする
- ログインのウィンドウは `code-viewer-login` セッションに開く。起動後は画面がログイン状態を
  強制的に取り直す期間を持つので、公式コマンドが成功した後の状態は一覧へ自動で反映される

### 登録・削除・表示名

- 既定の設定ディレクトリを「既存のディレクトリ」として登録する要求は拒否する。既定は登録簿に
  書く対象ではなく、常に固定の `Default` として一覧にある
- 登録したアカウントの削除は確認画面を出し、登録簿からだけ外す。管理下の設定ディレクトリにも
  認証・履歴があるため、code-viewer は消さない。動いているエージェントも止めず、一覧では
  未登録の設定ディレクトリとして扱う
- 登録したアカウントの表示名は変えられる（設定の Accounts の「名前を変更」、全体ボードの
  Accounts の帯のカードの ⋯）。変わるのは登録簿の `name` だけで、id・種類・設定ディレクトリ・
  `lastLaunch` はそのままなので、サイドバー・全体ボード・使用量の表示は登録簿を読み直して追従する。
  サーバ（`applyRenameAccount`）はロックの中で読む → 変える → 書く。規則は
  `core/agent-accounts.ts` の `renameAccount` 1 か所で、画面の押す前の検査も同じ関数を使う

  | 変えようとしたもの | 結果 |
  |---|---|
  | 既定のアカウント（`<種類>:default`） | 断る（`builtin`）。名前は画面の言語の `Default` / `既定` |
  | 空・60 文字を超える・制御文字 | 断る（`invalid`、理由の種類つき） |
  | `Default` / `既定`（大文字小文字を区別しない。`RESERVED_ACCOUNT_NAMES`） | 断る（`invalid`）。一覧で既定と見分けられないため。i18n の `defaultName` と一致することはテストが確かめる |
  | 同じ種類のほかのアカウントの名前（大文字小文字を区別しない） | 断る（`conflict`、重なった名前つき）。別の種類なら同じ名前でよい |
  | 自分の名前の大文字小文字だけの違い | 通す |
  | id・種類・設定ディレクトリ | 変えられない（変えるなら外して登録し直す） |

  追加（`checkAddAccount`）は今も名前の重なりと既定の名前を見ていない（名前の変更だけの規則）
- 別の登録アカウントを「既定」にする操作は**作らない**（決定）。「既定」は選べる属性ではなく、
  環境変数を渡さない `~/.claude` / `~/.codex` という固定の経路

### プロセスの環境変数（`server/accounts/process-env.ts`）

一覧の行のアカウントは、ペインのエージェントのプロセスの `CLAUDE_CONFIG_DIR` / `CODEX_HOME`
から求める。**プロセスの環境変数には API キーなどが入っている。**

- 取り出すのはこの 2 つだけ（`ACCOUNT_ENV`・`pickAccountEnv`）。ほかの変数は保持しない・
  返さない・ログに出さない・例外のメッセージに含めない。失敗の説明に使うのは終了コードと
  stderr だけで、`ps` の stdout は使わない
- 調べる頻度は抑える（ペインのシェルと前面のコマンドが同じなら `PROBE_TTL_MS` の間は
  調べ直さない）。一覧の応答を待たせないよう、古い値は裏で調べ直す
- 動作確認でもこの出力をファイルや画面に残さない。要るのは件数と 2 つの変数の有無だけ

### 使用量

| 種類 | 出どころ | 注意 |
|---|---|---|
| claude | statusLine に渡される JSON にしか上限の情報が無い。settings.json の `statusLine.command` を包み、受け取った JSON を `<状態ディレクトリ>/agent-usage/` に保存してから元のコマンドにそのまま渡す（`server/terminal/statusline.ts`） | 包む・戻すは 4 の部品と同じ約束・同じ確認画面。**包むスクリプトは元の出力と終了コードを必ず返す**（保存に失敗しても。失敗は同じ場所の `failures.log`）。動いているセッションが無いと更新されない |
| codex | `<CODEX_HOME>/sessions/` のセッション記録の `token_count` の上限情報（`server/accounts/usage.ts`） | **公式に約束された書式ではない。** 読めなければ理由つきで「取得できません」にし、0% や空欄にしない。mtime は読む候補を有界に絞るためだけに使い、解析後の新旧はイベントの `observedAt` で決める。大きなファイルは末尾だけ読む |

**使用量には必ず「いつの値か」を添える。** claude の値はセッションが動いているときにしか
更新されないので、古い値を今の値のように見せると使い切りを見誤る。

同じ設定ディレクトリの codex 記録を「別アカウントの値が混在」とするのは、同じ窓で新しい
reset が古い reset より許容差を超えて前へ戻るか、古い窓が新しい観測時刻にも終わっていない
のに別の reset が同時に見えている場合だけ。古い窓が終わった後、5 時間・週の次の reset へ
進むのは正常な更新であり、混在にしない。`primary` / `secondary` という位置から窓の種類を
推測せず、各要素の `window_minutes` で種類を決める。画面は応答の `windows` にある窓だけを
表示し、記録に無い 5 時間・週の窓を補わない。混在と判定したときは、観測時刻の新しい記録の
値を出し、応答の `mixed` に古い側の窓を載せ、カードに「混在」の札（ツールチップに古い側の窓と、
アカウントごとに設定ディレクトリを分ける案内）を付ける。

## 6. 起動

「新しいエージェント」は、tmux の新しいウィンドウ（セッションが無ければ新しいセッション）に、
実行するものを**引数の配列でそのまま渡す**（`core/agent-accounts.ts` の `tmuxLaunchArgs`、
`server/accounts/launch.ts`）。アカウントは `env` の引数で渡し、既定のアカウントは `env -u` で
変数を外す。

- **`send-keys` でコマンドを打ち込まない。** シェルの履歴や、そのシェルに入力中の別の文字に
  混ざる。パスに空白や引用符があっても 1 つの引数のまま崩れない
- 起動コマンドは種類ごとに変えられる（既定は `claude` / `codex`）。利用者がラッパーの
  コマンドやシェルの関数で動かしていることが普通にあるため。そのため起動は対話シェル
  （`$SHELL -i -c`）を通す
- 起動の画面の「実行:」は `CLAUDE_CONFIG_DIR=… claude` の形で**見せるだけ**
  （`launchCommandLine`）。実際の起動の仕方とは別の関数なので、片方だけ直さない
- 起動・ログインのウィンドウには `remain-on-exit failed`。すぐ失敗して閉じても理由が読める
- ログインのウィンドウは `LOGIN_SESSION` に置き、起動先の既定の候補から外す

## 7. プロジェクトの登録と切替

### 採った方式

**入口のサーバ 1 つ + プロジェクトごとの裏のプロセス（入口が取り次ぐ）。** 以前は
プロジェクトごとのサーバへ別のポートで移っていた（下の「以前の方式」）。切替は
「同じオリジンのままページを読み直す」（`location.assign('/p/<鍵>/…')`。iframe で
中央だけ差し替える案と試作で比べて、利用者が選んだ）。

- URL の鍵は根の実パスの `rootFileKey`（サーバ登録簿・起動ロックと同じ）。**鍵から根を
  引けるのは、登録簿の根・入口がそのプロセスの間に許した根（起動したディレクトリ・
  CLI の「このディレクトリを開いて」・作業ツリーの「開く」）・登録したプロジェクトの
  作業ツリーだけ**（`entry/projects.ts`）。URL を踏むだけで任意のパスのプロセスが起きない
- 前置きの無い画面の URL（`/`・古いブックマーク）は、最後に開いたプロジェクト
  （ユーザー単位の設定 `lastProjectRoot`）、無ければ起動したディレクトリへ転送する。
  別のプロジェクトを最後に開いていたら、古いブックマークはそちらで開く（完全には守れない）
- 一覧では、画面が選んでいるプロジェクト（要求の `PROJECT_HEADER`）が `current`、
  裏が動いているものが `running`（URL は `/p/<鍵>/`）、動いていないものが `absent`。
  `absent` の登録済みを「開く」と、入口が裏を起こしてから移る（サイドバーの「起動中…」）
- 裏は入口の pid と起動ごとの token を `entry.json` と `/_entry` の両方で確かめる。
  入口が居なくなると 10 秒待って自分で終わる。その間に新しい入口が `/_entry/adopt` で
  新しい token を渡し、古い pid が居なければ、そちらに付き直す
- 裏が落ちたら 502、起きなければ 503（理由と `server-logs/` の末尾）。画面は中央の面を
  「このプロジェクトのプロセスが止まっています」の空表示で覆い、理由の全文はダイアログの
  「詳細」に畳む（`views/backend-state.ts`）。SSE の繋ぎ直しで起こし直すのは 1 回まで
  （落ち続けるものを起こし続けない）
- 使っていない裏は止める（アイドル停止）。SSE の購読も取り次ぎ中の流れも無く、最後の要求から
  `--idle-stop` 秒（既定 10 分）経った入口の裏だけ。止めた裏は「落ちた」扱いにせず、次の
  要求で黙って起こす（画面は起こしている間「起動中」を出す）。状態の型（`starting` /
  `running` / `idle-stopped` / `unreachable`）と条件の細部は `server.md` の入口の節
- 裏を止めても、ターミナル（tmux・シェル）・未読・通知・フックの申告は残る（全部入口に居る）。
  **裏に、止めると消える状態を足さない。** タブを裏に回すと SSE を切る（`app.ts` の
  `shouldConnectEventSource`）ので、長く裏にあるタブの裏のプロセスも止まり、表に戻したときに
  起こし直す

### 以前の方式（1 つで完結するサーバを並べる。`--standalone` はこれ）

**プロジェクトごとにサーバを立てる作りのまま**、次を足していた。

- ユーザー単位の登録簿 `<状態ディレクトリ>/projects.json`（配列の順 = 利用者の並び順）。
  登録の鍵は git の本体の作業ツリーのルートの実パスで、一覧がペインを束ねる鍵と同じ。
  tmux から見つかったプロジェクトと登録したプロジェクトは 1 つにまとまる
- 「開く」は同じタブで移る。止まっていれば**登録済みのプロジェクトに限って**、既存の起動の
  仕組み（`server/worktree/open.ts` の起動・本人確認・停止）で起こしてから移る
- 左のサイドバーでは**プロジェクト名を押すと移る**（畳む / 開くは左の山形だけ。キーボードは
  Enter = 移る、左右 = 畳む / 開く）。いま見ているプロジェクトは選択中の見た目で、押しても
  何もしない（読み直さない）。**未登録のものは確かめずに登録してから移る**
  （`ProjectActions.open` の `confirmRegister: false`）。ヘッダの切替と全体ボードの「開く」は
  今までどおり確かめる。登録は ⋯ のメニューから外せる。未登録の区画の ⋯ には「登録」だけして
  移らない操作がある
- 移っても骨格が同じに見えるよう、テーマ・左のサイドバーの幅と畳み・畳んだプロジェクト・
  下パネルの高さは全プロジェクト共通の設定に置く（localStorage はオリジン = ポートごとなので
  移るたびに戻る）。初回描画用の控えだけを localStorage に置く（`views/shell/early-look.ts`。
  初めて開くポートには控えが無いので、そこでは既定の見た目で描き始める）
- （消した）起こしたポートをプロジェクトごとに覚え、次も同じポートで起こしていた。通知の
  許可と localStorage がオリジン（ポート）ごとだったため。入口でオリジンが 1 つになったので
  消した。以前の版が登録簿に書いた `port` は読み飛ばす
- 人に付く設定（`core/user-settings.ts` の `USER_SETTING_KEYS`）をユーザー単位の
  `<状態ディレクトリ>/settings.json` に置く。移っても見た目と操作が変わらないように

### 以前捨てた 2 案と、その後

2 つ目の案（入口が中継する）は、下の理由でいったん捨てたが、取りこぼしを機械で止める
検査（`api-url-guard.test.ts`: フロントの経路の文字列は `core/api-url.ts` だけ）を先に入れ、
前置きを `apiUrl()` の 1 か所で付ける形にして採った。1 つ目の案（1 プロセスで全リポジトリ）
は今も採らない（裏の中身を `createRepoContext` のような入れ物へ移すのが先）。

| 案 | 捨てた理由 |
|---|---|
| 1 つのサーバが複数リポジトリを扱う | サーバがリポジトリを決め打ちしている箇所が多すぎる。`preview.ts` のモジュール変数 `cwd` と、そこに付くキャッシュ・ファイル監視・SSE の世代を全部「リポジトリごとの入れ物」に移す必要があり、移し損ねると**別のリポジトリの内容を返す**（キャッシュのキーにルートが入っていない）。さらにどの要求がどのリポジトリかをブラウザが伝える必要があり、下の案のフロント側の作業も全部含む。途中の状態で入れられない |
| 1 つの入口サーバがプロジェクトごとのサーバへ中継する | オリジンは 1 つにできるが、フロントの絶対パス（`/_…` の文字列・`EventSource`・`index.html` の参照・ルートの組み立て・`history`）を全部前置き付きに直す必要があり、**取りこぼした 1 か所が入口の別の場所に当たる**。SSE・シェルのストリームの中継と、`sideEffectRequestAllowed` の Host・Origin の扱いも要る |

規模を確かめ直すときは数え方ごと実行する（数は機能が増えるたびに変わるので、ここには
7177b0c 時点の値を参考に置くだけ）:

```sh
grep -cw cwd web-src/server/preview.ts                                  # 112 行
grep -rlw cwd web-src/server --include=*.ts | wc -l                     # 65 ファイル
grep -rnE "^(let |const [A-Za-z_]+ = new (Map|Set|WeakMap))" web-src/server --include=*.ts | wc -l   # 119
find web-src -name '*.ts' -not -path 'web-src/server/*' -not -path 'web-src/test/*' \
  | xargs grep -hoE "[\"\`']/_[a-z_]+" | wc -l                        # 143
```

**この方式を捨てて上の 2 案へ移るなら、まず `/_…` を 1 つの関数に通す検査から入る**
（取りこぼしを機械で止めるため。`AGENTS.md` の How To Add A Rule）。

### 止めてよいサーバ

一覧から止められるのは **code-viewer が起こしたサーバだけ**（`canStopProjectServer`）。
利用者が自分で起動したサーバと、いま見ている画面のサーバ（入口の下では、いま選んでいる
プロジェクトの裏）は止めない（利用者の作業を勝手に落とさない・自分の足場を消さない）。
入口が起こした裏にも同じ印が付く（起こす仕組みが同じ）。入口は登録簿に生きたサーバが
あればそれを使う（利用者が `--standalone` で起こしたものでも）。

見分け方: 起こすときに環境変数 `CODE_VIEWER_LAUNCHED_BY`（`LAUNCHED_BY_ENV`）を渡し、
起こされたサーバは起動時にそれを読んで**すぐ自分の環境から消し**、サーバ登録簿に
`launched: true` を書く。すぐ消すのは、残すとそのサーバのブラウザシェルに印が引き継がれ、
利用者がそのシェルから自分で起動したサーバまで「起こされた」扱い（= 一覧から止められる）に
なるため。作業ツリーの画面から起こしたサーバにも同じ印が付く（起こす仕組みが同じ）。

### 全プロジェクト共通の設定

- **ユーザー単位のファイルがあれば、その項目はそれだけを使う。** リポジトリの値へは戻らない。
  戻ると、ある画面で既定に戻した設定が、別のリポジトリの古い値で復活する
- ファイルがまだ無いとき（この版を初めて使うとき）だけ、最初に設定を読んだサーバの
  リポジトリの値を引き継いで作る。見た目が突然変わらないように。そのため
  `/_state/settings` の GET が初回だけファイルを書く
- リポジトリの設定ファイルは読むだけで、書き換えも削除もしない。閲覧済みの印・注釈・
  画面ルールの上書きなど、リポジトリの中身に付くものはリポジトリごとのまま
- 壊れたファイルは上書きしない。理由を返し、その間はリポジトリの設定で表示する

### 複数のサーバが同じファイルを書く

登録簿・ユーザー単位の設定・サーバの起動は、別々のリポジトリで動く複数のサーバが同時に
読み書きする。読んで・変えて・書く間は `server/file-lock.ts` のロックで囲む
（`createJsonFileStore` の直列化はプロセスの中だけ）。持ち主のプロセスが居ない・古すぎる
ロックは奪う。**ユーザー単位のファイルを足すときは、このロックと `registry-file.ts` の
読み方を使う。** 既存の書き方は次のとおり。

- フックと statusLine の設定変更は `commitJsonSettingsChange` がリンク先の実パスの
  `<realPath>.lock` を取り、ロック内で読み直して、確認時の hash・実パス・ファイル identity を
  全て照合してからバックアップと置換を行う
- アカウント登録簿は `updateAccountRegistry` が実パスの `<realPath>.lock` を取り、ロック内で
  読み直してから変更・保存する
- 画面ルールの移行・再読込・保存・初期化は `withAgentScreenRulesLock` という同じ実パスの
  ロックを共有する。保存と初期化は、本体の変更より先に移行済みの印を書き、途中で止まっても
  古いリポジトリのルールが復活しないようにする

### 古い版と混ざったとき

`code-viewer` は `entry.json` の入口の版が違えば、その pid と URL を出して起動しない
（止めない。止めるのは利用者）。版の違う裏は、入口が居なくなった後に新しい入口へ付き直さない。

古い版のサーバはユーザー単位の設定もプロジェクトの登録簿も知らない。その画面でテーマを
変えても新しい版には反映されず（逆も同じ）、その画面で「読んだ」ものはほかのサーバへ
中継されない。既知の限界として受け入れている（直す手段は、古い版を止めることだけ）。

## 8. 状態の置き場所

`<状態ディレクトリ>` = `codeViewerStateDir()`（`server/user-state-dir.ts`）=
`$XDG_STATE_HOME/code-viewer`、無ければ `~/.local/state/code-viewer`。キャッシュ
（`~/.cache`）に置かないのは、掃除で消えるとエージェントの設定に書いた呼び先を失うため。

| 置き場所 | 中身 | テストで逃がす環境変数 |
|---|---|---|
| `<状態>/agent-hooks/` | フックの起動スクリプト・`failures.jsonl` | `CODE_VIEWER_TEST_STATE_DIR` |
| `<状態>/accounts.json`・`<状態>/accounts/` | アカウントの登録簿・「新しく作る」の設定ディレクトリ | 同上 |
| `<状態>/agent-usage/` | statusLine を包むスクリプト・claude の使用量・`failures.log` | 同上 |
| `<状態>/projects.json` | プロジェクトの登録簿 | 同上 |
| `<状態>/settings.json` | 全プロジェクト共通の設定 | 同上 |
| `<状態>/main-tabs.json` | メインの面のタブの配置をプロジェクト（根のパス）ごとに。ファイルの包みは version 1、各配置は version 3（`core/main-tabs.ts` の `LAYOUT_VERSION`。左右で同じファイルを開ける）。配置の version 1・2 も読み（repo の page のタブは落とし、右の page のタブは左へ移す）、次の保存で 3 にする。3 より新しい版は使わず上書きもしない（`isNewerLayoutVersion`）。`/_state/tabs`、`server/main-tabs-store.ts`、`core/main-tabs.ts` の `parseLayout`。読めない配置は上書きせず、先に `POST /_state/tabs/backup` で同じ場所の `main-tabs.json.broken-<時刻>` へ写してから空で始める（写せなければ保存しない。理由は console.error）。`/_state/tabs`、`server/main-tabs-store.ts` の `backupMainTabs`、`core/main-tabs.ts` の `parseLayout` | 同上 |
| `<状態>/server-logs/` | code-viewer が起こしたサーバ・裏の出力（起動に失敗したとき・落ちたとき末尾を理由に添える） | 同上 |
| `<状態>/entry.json`・`entry.json.start.lock` | 動いている入口の `{url, pid, token, version, started_at}` と起動の排他 | 同上 |
| `<状態>/agent-screen-rules.json`・`agent-screen-rules.migrated` | 画面ルールの保存済み上書き（ユーザー単位）と、リポジトリから写した・保存した・戻した印 | 同上 |
| `~/.cache/code-viewer/servers/` | サーバ登録簿（1 リポジトリ 1 ファイル、起動ロック） | `CODE_VIEWER_TEST_SERVER_REGISTRY_DIR` |
| `<リポジトリ>/.code-viewer/settings.json` | リポジトリごとの設定（ユーザー単位の項目は初回の引き継ぎ元） | テストは一時ディレクトリのリポジトリで |
| `<リポジトリ>/.code-viewer/agent-screen-rules.json` | 以前の画面ルールの上書き。ユーザー単位のものが無いときに 1 度だけ写す（読むだけ） | 同上 |
| エージェントの設定ディレクトリ | フック・statusLine を書き込む先（4・5） | テストは一時ディレクトリを設定ディレクトリとして渡す |
| サーバのメモリ（入口） | 状態の記録・巡回の観測・未読 | — |

**新しいユーザー単位のファイルは `codeViewerStateDir()` の下に置く。** そうすれば
`scripts/vitest-global-setup.mjs` と `scripts/node-smoke.mjs` が既に一時ディレクトリへ
向けているので、テストもスモークも最初から実データに触らない。別の根（`~/.cache` など）が
どうしても要るなら、`CODE_VIEWER_TEST_*` の変数を足し、**両方のスクリプトに入れる**。
確認: `grep -rn "homedir()" web-src/server` で、状態ディレクトリと登録簿以外に
code-viewer 自身のファイルの置き場所を作っている箇所が無いこと。

置き場所を 1 つ足すときの手順:

1. `codeViewerStateDir()` から道を作る関数を 1 つだけ置き、呼び出し側はそれを使う
   （道を組み立てる箇所を散らすと、テストで逃がし損ねる）
2. 複数のサーバが同じファイルを書くなら 7 の「複数のサーバが同じファイルを書く」
3. 壊れたファイルを上書きしない（読めない理由を返す）。これまでの登録簿・設定と同じ扱い
4. 上の表に行を足す
5. 利用者の環境に残り、機能を消しても残るもの（エージェントの設定ファイルに書いた呼び先
   など）なら、`server.md` の「外部状態を変える機能」に従って doctor に検出行を足す
6. `pnpm run verify` の前後で、実際の状態ディレクトリと登録簿の更新時刻が変わっていない
   ことを記録する（9 の表の最初の事故）

## 9. 事故とその防ぎ方

この領域で実際に起きたこと。既存の reference に規範があるものはそちらを指す。

| 起きたこと | 防ぎ方 |
|---|---|
| `pnpm run verify` の中の CLI 起動スモーク（`scripts/node-smoke.mjs`）が登録簿を逃がさずに本物のサーバを起こし、起動時の片付けが、ある開発者の実際のサーバ登録簿から 160 件を消した | 新しい置き場所は最初から逃がせる形にする（8）。`vitest-global-setup.mjs` と `node-smoke.mjs` の**両方**を見る。verify・スモーク・動作確認の前後で、実際の状態ディレクトリと登録簿が変わっていないことを記録する（中身を読まず、更新時刻と件数で足りる） |
| テストが開発者のサーバ登録簿に書き、強制終了で消えずに 6,000 件以上溜まっていた。フックは申告のたびに全件を読むので、その数だけ遅くなった | 同上。テストが環境変数を後始末で消すと元の場所に戻るので、後始末では元の値に戻す |
| 設定ファイルのリンクを 1 段目だけ見て「書けない」と誤って報告した | 4 の「最後までたどった先で判断する」 |
| 作業中に `web-src/core`・`web-src/server` を編集するたび、開発者が `pnpm dev` で使っているサーバが再起動した（状態の記録・見始めた時刻が消え、`serverInstance` が変わる）。`pnpm dev` が入口になってからは、入口の再起動のたびに裏（開いているプロジェクト全部）も起き直し、シェルと未読も消える | 何を編集すると再起動するかは `orientation.md` の dev サーバの表。検証は別ポート・一時ディレクトリで起こした自分のサーバで行う（10）。使われているサーバの横で core / server を編集するなら、回数を減らし、編集したことを伝える |
| `biome check --write` を広い範囲に掛け、無関係なファイルの import の並びまで書き換えた（2 回） | `orientation.md` のコマンドの表。対象のファイルだけに掛ける |
| `TMUX` 変数が残ったシェルで広いパターンのプロセス終了と tmux のサーバ終了を行い、利用者の tmux まで止めた | `pkill -f`・`killall` と tmux の `kill-server` / `kill-session` / `kill-window` / `kill-pane` は使わない。専用ソケットを明示した読み取りだけを行い、止めるのは自分が起動時に控えた pid への `kill <pid>` だけ（10） |
| 分離した tmux の検証で AI CLI の裸のコマンド名を起動し、PATH 上の本物を実行した | PATH に同名ファイルを置くだけにせず、起動コマンドには自分で作った偽実行ファイルの絶対パスを設定する（10） |
| 2 つのアカウントに同じ設定ディレクトリを使い、使用量の記録が混ざった | 登録時の実パス重複検査を通し、検証ではアカウントごとに別の設定ディレクトリを作る。使用量は `observedAt` と窓ごとの reset で混在を判定し、最新の記録の値に「混在」の札と、混ざった側の窓・専用ディレクトリへ分ける案内を付ける（5。`server/accounts/usage.ts` の `mixed`、`views/agents/usage-meter.ts` の `usageMixedText`） |

## 10. 確かめ方の型

実データ（利用者の tmux・エージェントの設定・状態ディレクトリ・登録簿）に触らずに、
この領域を動かして確かめる手順。パスは例。自分の一時ディレクトリに読み替える。

1. **一時ディレクトリを 1 つ作り、`HOME`・code-viewer の状態・登録簿・tmux を逃がす。**
   `HOME` を差し替えるのは、既定のアカウント（`~/.claude`・`~/.codex`）とその使用量・フックの
   設定を読み書きさせないため。`PATH` は差し替えない（限った `PATH` では git や tmux が
   見つからない・別の git を拾うことが実際にあった）

   ```sh
   CV_SANDBOX_DIR=$(mktemp -d)
   mkdir -p "$CV_SANDBOX_DIR/home" "$CV_SANDBOX_DIR/state" "$CV_SANDBOX_DIR/registry" \
     "$CV_SANDBOX_DIR/tmux" "$CV_SANDBOX_DIR/libexec" "$CV_SANDBOX_DIR/work/sample-app"
   export HOME="$CV_SANDBOX_DIR/home"
   export CODE_VIEWER_TEST_STATE_DIR="$CV_SANDBOX_DIR/state"
   export CODE_VIEWER_TEST_SERVER_REGISTRY_DIR="$CV_SANDBOX_DIR/registry"
   export TMUX_TMPDIR="$CV_SANDBOX_DIR/tmux"
   unset TMUX TMUX_PANE XDG_STATE_HOME CLAUDE_CONFIG_DIR CODEX_HOME
   ```

   `TMUX_TMPDIR` はアプリが起動する tmux を分離し、`TMUX` を外すのは親のソケットへの接続を
   防ぐ。tmux を直接調べる必要があるときも、`env -u TMUX -u TMUX_PANE tmux -S <この検証で
   作ったソケットの絶対パス> …` という読み取り専用の形だけを使う
2. **偽のエージェント実行ファイルを作り、起動コマンドにその絶対パスを設定する。** 種類は
   ペインの前面のコマンド名で決まる（`agentKindOf`）ので、調べる種類と同じ basename の
   実行ファイルが要る

   ```sh
   cp "$(node -p process.execPath)" "$CV_SANDBOX_DIR/libexec/claude"
   ```

   Settings → Accounts → Launch commands には
   `$CV_SANDBOX_DIR/libexec/claude -e 'setInterval(() => {}, 1 << 30)'` のように絶対パスを入れる。
   `claude` のような裸の名前は、PATH 上の本物を起動するので使わない。node の写しにしているのは、
   basename を保ったまま動かせるため。画面の状態を変えるには、画面を描く自作スクリプトを
   同じ絶対パスから動かす
3. **フィクスチャの repo を作り、別ポートでサーバを起こす**（`sample-app` のような中立な
   名前。利用者のサーバのポートを使わない）

   ```sh
   node dist/code-viewer.js --cwd "$CV_SANDBOX_DIR/work/sample-app" \
     --port <空いているポート> &
   CV_SERVER_PID=$!
   ```

   アイドル停止を確かめるなら `--idle-stop 20` のように短くする（止めた・起こし直したは
   入口の出力に `[code-viewer] entry: …` の 1 行ずつ）。裏の状態は
   `curl -H 'X-Code-Viewer-Project: <鍵>' <入口>/_entry/backend` で読める。
   複数のサーバ・プロジェクトの切替を見るなら、repo を 2〜3 個作って同じように起こす。
   フックの申告は、設定ファイルに書かれたコマンドを公式どおりの入力（フックに渡される
   JSON）で `sh -c` に渡して手で実行する
4. 終わったら、自分が起動時に控えた `CV_SERVER_PID` だけを `kill "$CV_SERVER_PID"` で止める。
   分離した tmux は終了操作をせず残す。一時ディレクトリも、その tmux が残っている間は消さない
5. `pnpm run verify` と `npm pack --dry-run` の逃がし方は `testing.md` の vitest 事情の表の
   後ろ。前後で実データの更新時刻が変わっていないことを記録する

画面の確認そのもの（DOM と `getComputedStyle` を読む・ライトとダーク・密度）は
`diagnose.md` の「UI を実画面で確認する」。

## 11. 後回しにしたこと・既知の限界

| 項目 | 現状と理由 |
|---|---|
| 使っていない裏の自動停止 | 入った（7）。止めるまでの時間は CLI の `--idle-stop` だけで、設定画面には出していない。入口を起動し直すと数え直す（前の入口が数えていた時間は引き継がない）ので、拾い直した裏はそこから `--idle-stop` 秒後に止まる |
| 未読 | サーバのメモリ（3）。サーバの再起動では消える |
| アカウントの追加のときの名前の重なり | 名前の変更は同じ種類の重なりと既定の名前を断るが、追加はまだ見ていない（5 の登録・削除・表示名）。既定の付け替えは作らないと決めた |
| 起動時に `--settings` でフックを渡す | 作っていない。設定ファイルが書けない人向けの別の入れ方になりうる |
| tmux の巡回を 1 本にまとめる | 入口の下では入口の 1 本だけ。`--standalone` と古い版が並ぶ間はそれぞれが巡回する（見られていないサーバを遅くする仕組みで抑える） |
| 前置きの無い古いブックマーク | 最後に開いたプロジェクトへ転送するので、別のプロジェクトを最後に開いていればそちらで開く |
| worktree の 2 段表示 | worktree は本体のプロジェクトにまとめ、行に worktree 名を出すだけ |
| 通知はタブを開いている間だけ | ブラウザの通知なので、code-viewer のタブが 1 つも無ければ出ない。長く裏にあるタブはブラウザがタイマーを間引くので遅れる（ブラウザの仕様。遅れの幅は測っていない） |
| `ps` の出力の切り方 | `ps eww` は区切りを持たないので、値の終わりを「空白 + `名前=`」で決めている。パスに ` NAME=` の並びがあると切り損なう。起動後に環境が変わった場合やセッション中のアカウント切替は見えない |
| 内部形式に頼っている箇所 | codex のセッション記録（使用量）、エージェントの画面の文言（状態）。どちらも版が上がれば壊れうる。壊れたら理由つきで「取得できません」・画面ルールの修正（2） |
| 画面ルールの保存済み上書き | ユーザー単位に移した（8）。`--standalone` のサーバもユーザー単位のものを読むので、並んでいても同じルールで判定する |
| xterm の代替画面の行数の上限（上流の不具合。6.0.0 と上流の main で同じ） | xterm は、一度も使っていない代替画面（tmux・vim・less が使う画面）を縮めても、その画面の行数の上限を縮めない。上限が画面より大きいまま tmux が代替画面へ入ると、画面に無いはずの行が溜まり、次に行数が変わったときに画面の起点がずれて、最後の行が重複して並ぶ。回避は `terminal-screen.ts` の `attach` で「寸法を合わせてから `reset`」の順にすること（`reset` は今の寸法で両方の画面を作り直す。順番は `terminal-screen-resize.test.ts` が見る）。**残る限界**: tmux を使わない素のシェルで、代替画面に入っていない間に下のパネルを低くしてから vim などを起動すると、同じ崩れが起きうる（公開 API では上限を直せない）。開き直す（タブを行き来する・再読み込み）と `attach` が作り直すので直る |

## 12. ターミナルの画像の棚

ターミナルの出力に出た画像パスを、画面の右の細い列（棚）に新しい順のサムネイルで並べる。
置き場所: `views/terminal/image-shelf.ts`（描く）・`image-shelf-list.ts`（並びの決まり）・
`terminal-screen.ts`（拾う・問い合わせる・リンク）・`core/terminal-images.ts`（拾い方と型）・
`server/terminal/images.ts`（配ってよいかの判定）・`image-base.ts`（相対パスの起点）。

### 決めたこと

- **画像を端末の文字の上に重ねない。** 以前はパスの 1 行下に画像を重ねていて、パスの下の行・
  作業中の行・入力欄・statusline が隠れた。棚は端末の画面の箱の中で別の列として場所を取る。
  パスは xterm のリンク（`registerLinkProvider`）にし、カーソルが載ったら棚の同じ画像を強調して
  棚の中だけをスクロールする（端末のスクロールと入力は触らない）。リンクは描き直しのたびに
  xterm が聞き直すので、全画面を描き直すアプリ（tmux）の下でも位置がずれない
- 開く口は `terminal-screen.ts` の `openShelfEntry` 1 つ（今は拡大表示 `image-lightbox.ts`。
  棚の並びを ←→ で回れ、パスをコピーできる）。画像のタブができたらここを差し替える
- 棚が無い（画像が 0 件）ときは列ごと出さない。畳んだかどうかはユーザー単位の設定
  （`terminalImageShelfCollapsed`）
- 並び: 見つけた順番の新しい順。同じ実体（symlink を解いたパス）は 1 つ。更新時刻か大きさが
  変われば先頭へ（エージェントは同じ名前で上書きする）。上限 `MAX_SHELF_IMAGES` を超えたら
  古いものから落とす。1 回で届いた出力（繋いだ直後やアプリの描き直しは画面全体が 1 回で届く）
  の中では、最後に出てきた位置で並べる
- 拾い方: 繋いだときに 1 回、シェルが映している tmux のペインの履歴を
  `TERMINAL_IMAGE_HISTORY_LINES` 行さかのぼる（`/_agent/images/history`。履歴で見つけたものは、
  繋いでから出力で見つけたものより下）。その後は出力の流れを走査する。同じ綴りを聞き直すのは
  `IMAGE_REQUERY_MS` 空けてから（全画面アプリの下では同じ画面が続けて届く）
- 読めなかったものは理由つきで棚に残す（大きすぎる・読めない・通常のファイルでない・空）。
  「無い」だけは、棚に既にある画像が消えたときに限って出す（拾う候補は拾い過ぎる前提で、
  知らない候補の「無い」まで並べると棚が誤検出で埋まる）
- 相対パスはシェルが映している tmux のペインの作業場所（`pane_current_path`）から解く。
  シェルとペインは端末の名前（`ShellSession.tty` と `#{client_tty}`）で突き合わせる。取れない
  ときだけ シェルを起こした場所 → リポジトリの根 の順に戻る。tmux の失敗は応答の
  `base.error` とログに残す
- サムネイルはブラウザに縮小させる（依存を足さない。サーバで縮小しない）。URL に更新時刻と
  大きさ（`v=`）を入れ、それが今の実体と一致するときだけ `/_agent/image` が
  `Cache-Control: private, max-age=…, immutable` を返す（一致しなければ今までどおり `no-store`）

### 安全の条件（緩めない）

`/_agent/image` はリポジトリの外のファイルも配る（エージェントは一時ディレクトリに書くことが
多い）。その代わり、配るのは `resolveTerminalImage` を通ったものだけ:

- 拡張子の許可リスト（PNG・JPEG・GIF・WebP。SVG は中にスクリプトを書けるので外す。
  貼り付けと同じ表 `TERMINAL_IMAGE_EXTENSIONS`）
- symlink を解いた実体が通常のファイル（ディレクトリや名前付きパイプを配ろうとすると詰まる）
- 0 バイトでない・上限（`MAX_PASTE_IMAGE_BYTES`）まで・読める
- 配るたびに判定し直す（クライアントが持って回った URL を信用しない）。ヘッダは `/_file` と同じ
  `rawFileHeaders`（`nosniff`・`CSP: sandbox`）

新しい経路や引数（起点・版・履歴）を足すときも、ファイルに触る前に同じ判定を通す。起点を
変えても許す範囲は変わらない（相対パスの解き方が変わるだけ）。失敗の理由は
`TerminalImageRejectReason` で区別して返す（`null` 1 種類に潰さない）。

### 既知の限界

| 項目 | 現状 |
|---|---|
| 棚はブラウザのタブのメモリだけ | 読み直すと、履歴をさかのぼれる範囲まで戻る。消えた画像の「無い」も読み直すと出ない（知らない候補になる） |
| シェルの端末名が空のままになることがある | `server/shell/session.ts` の `resolvePtyTty` は spawn 直後から 2 秒まで再試行し、その後も `shownInShell` の照合時に取り直す。それでも環境が TTY を返さなければペインが分からず、相対パスはシェルの場所から解き、履歴もさかのぼれない |
| リンクの下線はカーソルが載ったときだけ | xterm のリンクの描き方。常に下線を引くには decoration が要り、tmux の描き直しの下で位置が安定しない |
| 棚の幅は密度で比例して変わる | 既定の密度で 132px。compact 115.5px・xlarge 165px（`--space-unit` から作るため） |

## 既存の違反をどう扱うか

**触ったら直す。** 変更した箇所が上の決まり（全サーバへ送る・環境変数は 2 つだけ・
設定ファイルは `settings-file.ts` を通す・状態ディレクトリの下に置く・経過時間を断定しない）
から外れていたら、その変更で揃える。**まとめて直すのは別作業。** 見つけた違反は報告する。

## やってはいけないこと

| 違反 | 結果 |
|---|---|
| 申告や「読んだ」を、いま開いているサーバにだけ送る | サーバごとに状態が食い違い、移ると未読がよみがえる |
| 状態・未読・シェルを裏のプロセスに持たせる | 裏はプロジェクトごと・止められるものなので、移ると・止めると消える。入口に置く |
| 画面の観測で申告の `done` を消す | 終わったことに気付けなくなる |
| 作業中の行を下からの行数で探すルールを書く | 利用者のステータス表示の行数で外れる（実際に外れた） |
| プロセスの環境変数を、2 つの変数以外まで保持・ログ出力する | API キーが漏れる |
| 認証ファイル（`auth.json`・`.credentials.json`・キーチェーン）を開いて「誰として」を得る | 秘密に触る。出さないと決めてある |
| 設定ファイルを `settings-file.ts` を通さずに書く | バックアップ・ハッシュ照合・リンクの扱いのどれかが抜ける |
| リンクの 1 段目だけを見て書ける・書けないを決める | 誤った報告・誤った案内になる（実際に起きた） |
| フックの設定ファイルに code-viewer の場所を直接書く | 版が上がるたびに設定ファイルが変わり、codex が信頼し直しを求める |
| 新しい置き場所を `codeViewerStateDir()` の外に、逃がす変数なしで作る | テストとスモークが実データを書き換える（実際に 160 件消えた） |
| `send-keys` でエージェントを起動する | 利用者のシェルの履歴と入力に混ざる |
| 広いパターンでプロセスを止める / tmux のサーバ・セッション・ウィンドウ・ペインを終了する | 利用者の作業まで止める。止めてよいのは、自分が起動時に pid を控えたプロセスだけ |
| 検証用 tmux で AI CLI の裸のコマンド名を起動する | PATH 上の本物を実行する。自作した偽実行ファイルの絶対パスだけを使う |
| ターミナルの文字の上に画像やツールチップを重ねる | パスの下の行・入力欄・statusline が隠れる（実際に「見づらい」と言われて棚に移した） |
| 端末に出たパスを `resolveTerminalImage` を通さずに読む・配る | 許可していない種類・大きさ・ファイルでないものを配る |
| 使用量を「いつの値か」なしで出す / 読めないときに 0% と出す | 古い値や失敗を今の値として信じさせる |
